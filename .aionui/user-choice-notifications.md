# User-choice notifications

Feature ID: `prose-user-choice-notifications`. Preserve this behavior across repeated upstream rebases, not particular commits or selectors.

## User-visible contract

- A real prose question requiring a user choice, approval, or answer is accompanied by a standalone `[[AIONUI_USER_CHOICE_REQUIRED]]` line. This includes a new approval request at the end of a plan, review, or progress report before starting implementation or applying a proposed change. Arbitrary question wording is not classified heuristically.
- Codex non-blocking structured questions use the same notification list without a prose marker. AionCore recognizes `agentMessage` items with `delivery: "async"` and valid `questions`, preserves each title/options as a separate text message, and registers the notice after that message is persisted. Repeated item IDs use stable conversation/item/question identities so replay cannot duplicate bubbles or revive dismissed notifications. These events do not open a blocking permission request; users answer in the conversation as before.
- The global titlebar bell is labeled **User attention needed** and combines prose questions with unread terminal errors. It counts distinct conversations across both sources, independent of bookmarks, history period filters, or collapsed sidebar. Both types remain separate entries when they belong to the same conversation. Desktop/tablets use a popup; narrow phones use a bottom sheet.
- Selecting a question entry opens its originating conversation and navigates to its persisted message and marker index. Navigation waits for history loads and a mounted row, then scrolls the chat container directly to the selected marker inside rendered Markdown (including its shadow root). Resize and mutation observers keep that target visible through delayed images, Markdown rendering and history layout changes; bottom-following and prepend compensation yield while it owns the scroll position. Wheel, pointer, touch and scrolling keys release the target, as do a new user message, another explicit jump, bottom-follow and route changes. Another notification click can repeat the jump or retry a failed/missing anchor. It does not dismiss the question or add composer focus behavior.
- Sending a user message, including mid-turn delivery, leaves question notifications pending. Programmatic agent turns, hidden messages, opening the conversation, finishing/interruption, and any AI resolution marker also leave them pending. Only the user's explicit **Dismiss notification** action clears a question; it removes only the selected entry and is not an approval, reply, or command to an AI. A delayed registration remains pending even if a user message was persisted after the question.
- Error entries show their provider reason (or the existing error fallback), open the failed conversation, and acknowledge the same per-turn read receipt as the sidebar. Dismissing an error also acknowledges that receipt. Reading an error never dismisses an independent question or retries/approves an AI action. Sidebar reads and notifications stay synchronized, including reload recovery; do not duplicate failure state in the choice store.
- AionCore owns pending entries and durable dismissal/supersession tombstones per backend user. Every device loads the same snapshot when it opens, and connected devices replace their local mirror from `conversation.choiceNoticesChanged` events. Previously resolved entries and legacy browser-local v1 queues are not restored; the manual-dismissal policy applies to pending and newly registered questions.
- The conversation's separate warning badge coexists with its original provider identity, spinner, and bookmark. A collapsed project group shows a warning alongside its existing aggregate status. Both All and Bookmarks supply their collapsed group members. Titles may truncate to reserve right-side space; left-side geometry stays unchanged.
- Only visible assistant text is inspected. User messages, thinking, tool output, hidden messages, teammate content, quoted/inline/indented/fenced examples do not register notifications. The same message's streamed fragments share stable notification keys; multiple markers in one message remain independently dismissible. An identical non-empty question repeated in a later assistant message replaces the older entry and navigates to the newer message.
- No polling, extra CLI invocation, natural-language inference, or changes to actual confirmation/approval state are introduced. Parser scratch buffers and previews are bounded.

## Instruction boundary (AionCore)

`aionui-ai-agent`'s fork-only `capability/user_choice_notice.rs` adds registration-only guidance to the outbound `AgentInstance` send and mid-turn delivery boundaries. The original persisted user message, attachment paths, correlation IDs, preset rules, and selected skills are unchanged. Slash commands are byte-identical. Existing conversations receive guidance on their next request; ongoing requests cannot retroactively receive it.

The guidance remains in English, but the entire response follows the user's explicitly requested language or the current conversation's language. The instruction's own language does not select the response language. A new prose approval request must identify the action and scope in an explicit marked question rather than end with an indirect offer to proceed after approval. An already marked request is not repeated merely as a reminder, and already authorized work does not acquire a new approval requirement.

The instruction preserves authority boundaries: unanswered choices do not authorize dependent actions, but previously authorized independent work may continue. Only the user's explicit dismissal clears a question notification; neither sending a reply nor an AI-generated marker clears it. AI adherence is best-effort; unit tests prove instruction delivery and explicit-marker UI behavior, not every model's future compliance.

## Structured-question boundary (AionCore)

The isolated `aionui-session/src/backend/codex_conn/user_questions.rs` adapter reads structured async metadata, and the session pump preserves it through `UserQuestion`. `aionui-conversation/src/stream_relay/user_questions.rs` stores independent text anchors and notices using the existing user-scoped snapshot and dismissal APIs. This works without an open conversation or a connected renderer. Question anchors stay outside terminal prose rewrites. Invalid/missing metadata falls back to the ordinary text path; plain unmarked prose is never guessed to be a question.

Verified protocol evidence: codex-cli 0.162.1 `app-server generate-json-schema --experimental` (`ItemStartedNotification`, `ItemCompletedNotification`, `AsyncUserInputQuestion`), plus the real `thread/read` item committed as `aionui-session/src/backend/codex_conn/user_question_01621.json`. Its matching rollout `item_completed` was captured on 2026-10-15. Notification wrappers in adapter tests are schema-derived, not presented as live wire captures. This change handles newly received question events; it does not backfill previously flattened history.

The frontend receives these notices through the existing snapshot subscription. Selecting one loads its standalone message with index zero; when there is no prose marker, `useMessageTargetScroll` aligns the start of the message instead of the center of a potentially long options list. Existing marker lookup and layout stabilization remain active.

## Native interactive questions (AionCore)

The existing `ask` event is persisted as one interactive card, with a stable conversation/request identity. Each question in that card receives its own notice and `data-choice-marker-index` target. Registration happens on the server after the card is queryable and does not require a connected renderer or an open conversation. This extends the existing event contract; it does not infer questions from prose or generic permission requests.

The dedicated answer endpoint records accepted answers or an explicit decline on the same card and broadcasts that state to other clients. It does not dismiss notices. Replays preserve the saved response and durable dismissal tombstones. Pending-confirmation recovery deduplicates transient cards against the persisted request; removing a pending confirmation retains the durable navigation anchor. Restored unanswered cards are disabled until the pending request is verified, and expired requests become read-only. No polling or automatic answer/approval is introduced.

For focused checks, run the native/async question relay tests and the choice-notice tests in `aionui-conversation`, plus the AionUi notification DOM and pending-confirmation recovery tests. The browser navigation fixture includes native multi-question cards with long first-question options and older-history loading. These are event/SQLite/browser tests; they do not claim a fresh live CLI capture.

## Rebase integration seams

1. Keep the isolated `UserChoiceNotifications` context feature mounted at the shared layout boundary. Retain exactly one global subscription each for `message.stream` and `conversation.choiceNoticesChanged` even when conversation routes or filters change. Do not subscribe to `message.userCreated` to clear question notifications.
2. Keep the titlebar trigger mounted outside the active-chat subtree and outside desktop-only gates. Verify touch breakpoints and native window drag exclusion.
3. Keep row warnings separate from `isWaitingConfirmation`: a prose question does not imply the agent has stopped. Keep warning placement clear of hover menus, unread dots, and collapsed identity/spinner geometry.
4. Reconnect both All and Bookmarks' collapsed group members if upstream moves history grouping. Do not treat group/filter visibility as notification resolution.
5. Keep the same outbound prompt guidance at normal and mid-turn send boundaries if AionCore reorganizes dispatch. Verify slash commands and persisted message content against the then-current implementation.
6. Preserve stable conversation/message/marker-index keys and AionCore's user-scoped persistence. Normal sends, mid-turn sends and delayed registrations must retain pending questions. Clear individual entries only through explicit dismissal, synchronized to other devices. Keep dismissal tombstones so delayed registration or replay cannot revive a dismissed entry. Do not replace this lifecycle with generic unread-clearing logic.
7. Keep localization keys in every supported locale and regenerate i18n types.
8. Preserve `useAttentionNotifications`' presentation-only combination and the `useUnreadConversationFailures` selector on the existing history store. Reconnect this small seam if upstream moves failure tracking. Both sources have distinct lifecycle and storage policies: never replace manually dismissed questions with automatically read failures or add another error-stream listener/polling loop.
